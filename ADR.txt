# ADR-000: 템플릿 캐릭터 클래스명 유지

- 2026-09-07 / 채택 / 2주차 D1

- 배경 : 
설계 문서(GDD §9)에는 플레이어 클래스를 APlayerCharacter로 계획했으나, 3인칭 C++ 템플릿이 생성한 실제 클래스는 AStealthCharacter였다. 
첫 코드 작업 전에 이름을 맞출지 결정이 필요했다.
- 선택지 : 
A - 클래스명 유지, 문서를 코드에 맞춤 (비용 0 / 문서와 계획 문서 간 불일치를 수정해야 함)
B - C++ 클래스를 APlayerCharacter로 리네임 (문서와 일치 / 파일명·클래스명·생성자·.generated.h·BP 부모 참조를 모두 맞춰야 하고, 하나라도 어긋나면 프로젝트가 열리지 않는다)
C - APlayerCharacter : AStealthCharacter 상속 (리네임 위험 없음 / 상속 단계가 하나 늘어 이득 없이 복잡해짐)
- 결정 : 
A. 
- 근거 : 
리네임은 기술적 이득이 0이고 프로젝트 파손 위험만 있다. 개발 1일차에 도구 체계도 익숙하지 않은 상태에서 감수할 이유가 없다.
- 결과 : 
GDD와 변경 이력을 수정

# ADR-001: 코드 주석을 영어로 작성

- 2026-09-08 / 채택 / 2주차 D2

- 배경 : 
한글 주석을 넣고 저장하자 Visual Studio가 인코딩 변경 여부를 묻는 창을 띄웠다. 
템플릿 소스는 ANSI(CP949)로 저장되어 있고, MSVC는 BOM이 없으면 파일을 시스템 기본 코드페이지로 해석한다.
- 선택지 : 
A - 파일을 UTF-8 with signature로 저장 -> 새 클래스를 만들 때마다 같은 처리 반복. 파일별 인코딩이 섞임
B - 코드 주석은 영어, 학습 노트는 한글로 분리 -> 없음
- 결정 : 
B. 코드 주석과 커밋 메시지는 영어, Docs/notes/의 학습 기록은 한글.
- 근거 : 
인코딩 처리를 매번 반복할 필요가 없다.
GitHub 공개 저장소다. 12월에 README·기술문서와 함께 열람 대상이 되며, 한글 주석은 열람자를 제한한다.
- 결과 : 
주석 사본(*_annotated.cpp)만 예외. .gitignore에 추가하여 커밋하지 않는다.
주석은 대개 명사구라 영어 부담이 낮다

# ADR-002: 이동 상태를 단일 enum으로 설계

- 2026-09-08 / 채택 / 2주차 D2

- 배경 : 
플레이어의 이동 상태(웅크리기 / 걷기 / 달리기)를 코드에서 어떻게 표현할지 결정이 필요했다. 
- 선택지 : 
A - bool 플래그 조합 (단순함 / 조합 4가지 중 1가지가 무효 상태. 둘 다 true인 모순이 컴파일 단계에서 걸러지지 않는다)
B - gait / stance 2축 분리 (앉아서 걷기와 앉아서 달리기를 별도로 표현 가능 / 조합 6가지. 흔적 규칙을 조합마다 정의해야 함)
C - 단일 enum 3값 (불가능한 상태가 존재할 수 없음. 흔적 규칙 3개 / 앉아서 달리기를 표현할 수 없음)
- 결정 : 
C. EMovementStance { Crouch, Walk, Sprint }
- 근거 : 
두 축이 독립적이지 않다. 업계 표준이 gait와 stance를 나누는 이유는 조합이 각각 의미를 갖기 때문인데, 이 게임은 그렇지 않다.
-> 웅크린 자세와 잠입 상태가 1:1로 대응한다. 앉은 모습 자체가 "지금 흔적을 남기지 않고 있다"는 시각적 신호다.
-> 웅크린 상태에서는 이동 속도가 하나로 고정된다. 앉아서 달리는 상태는 게임 규칙상 존재하지 않는다.
또한, 불가능한 상태를 애초에 만들 수 없게 하는 것이 런타임 검사보다 낫다. A안은 모순 상태를 코드로 방어해야 하지만 C안은 타입 시스템이 막는다.
- 결과 : 
가능해진 것 : 6주차 흔적 시스템이 이 값 하나만 참조하면 된다.
포기한 것 : 앉아서 달리기. 게임 설계상 불필요.
부수 효과 : 명칭이 부정확하다. Crouch는 stance, Walk/Sprint는 gait이므로 EMovementState가 더 정확한 이름이다. 변경 여부는 미결

# ADR-003: 앉기 속도를 엔진 기능에 위임

- 2026-09-10 / 채택 / 2주차 D4

- 배경 : 
ApplyStanceSpeed()에서 웅크리기 상태일 때 MaxWalkSpeed에 앉기 속도(180)를 대입했으나 실제로는 300으로 이동했다. 
컴파일·실행·대입 모두 성공했고 오류도 발생하지 않았다.
원인 추적 결과, UCharacterMovementComponent는 bIsCrouched가 true이면 MaxWalkSpeedCrouched를 참조하고 MaxWalkSpeed를 무시한다. 
300은 엔진 기본값이었다.
- 선택지 : 
A - MaxWalkSpeedCrouched를 설정하고 엔진에 맡김 -> 앉기 속도만 다른 경로로 관리됨
B - Crouch()를 쓰지 않고 캡슐 크기·속도를 직접 제어 -> 캡슐 축소·바닥 위치 보정·메시 오프셋·네트워크 동기화를 전부 직접 처리해야 함
- 결정 : 
A. 생성자에서 MaxWalkSpeedCrouched = Speed_Crouch를 설정하고, ApplyStanceSpeed()의 Crouch 케이스는 비워둔 채 이유를 주석으로 남긴다.
- 근거 : 
엔진이 담당하는 영역에 중복 구현하면 오류 없이 조용히 무시된다. 이런 종류의 문제는 코드를 아무리 들여다봐도 틀린 곳이 없어 원인 추적이 어렵다.
- 결과 : 
case를 삭제하지 않고 비워둔 이유: 삭제하면 나중에 "앉기 처리가 빠졌다"고 판단해 다시 넣게 된다. 비어 있는 이유가 코드에 적혀 있어야 한다.
